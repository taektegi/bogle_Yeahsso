# 저장 복구·주문 보호·대화 기록 재시도

브랜치: release. 백엔드 변경 없음.

## 복구

- `readDocument`/`FileStore.readValidated`로 JSON 문법뿐 아니라 저장소의 모델 구조까지 검증한다. 캐릭터·주문·프로필·대화 문서에 적용했다.
- 캐릭터의 친구/상태/기억 필드와 주문의 주문/배송지/결제수단을 검증한다. 주문은 모든 목록의 복원이 성공한 뒤에만 상태에 반영한다.
- 본 파일이 구조적으로 손상돼도 정상 백업을 시도한다. 읽은 정상 백업을 다음 저장의 이전 저장본으로 사용하며, 값이 같더라도 손상된 본 파일을 다시 쓴다.
- 두 사본 모두 읽지 못하면 기존 파일을 덮어쓰지 않는다. 앱에서 문서별 영향 범위를 설명하고 ‘나중에’ 또는 ‘원본 보관 후 새로 시작’을 제공한다.
- 새로 시작하기를 선택한 경우 두 사본을 각각 `.corrupt-마이크로초` 파일로 **모두 복사한 뒤** 원래 위치를 비운다. 복사 실패 시 원본 삭제를 시작하지 않는다. 그림 파일이나 다른 문서는 초기화하지 않는다.
- 보류/실패 이후에도 캐릭터·주문·프로필 저장소는 같은 객체에서 복원을 다시 시도할 수 있다. 잘못된 재실행 안내를 제거했다.
- 문서 구조 검증 실패 상태에서는 직접 쓰기도 차단한다. 파일 권한·읽기 I/O 오류를 데이터 손상으로 취급해 초기화하지 않는다.
- 기존 null 문서(배경 캐시 비우기)와 레거시 대화 목록을 호환한다.

## 저장 비용

- 마지막 정상 텍스트를 최대 12문서/총 8M문자 범위에서 보관한다. 캐시가 있으면 쓰기 직전에 기존 파일을 다시 읽고 JSON 검사하지 않는다. 저장이 완료된 경우에만 캐시를 확정한다.
- 변경이 없는 정상 문서는 다시 쓰지 않는다. 기존 원자적 임시 파일 교체와 이전 정상본 백업은 유지한다.
- JSON 인코딩을 별도 isolate에서 수행하고, 64Ki문자 이상의 JSON 디코딩도 isolate에서 수행한다. 원본 읽기/백업/본 파일 쓰기가 모두 없어지는 것은 아니다.
- 대화는 첫 로드 후 메모리 기록으로 append/prepend한다. 저장 실패 시 메모리에는 성공한 척 반영하지 않는다.
- 실제 렌더링 성능/프레임 지연의 개선 배수는 측정하지 않았다. 대화 읽기 횟수와 대형 JSON 왕복을 테스트했다.

## 서버 기록

- 저장 형식 `{entries, serverImported}`를 사용한다. 예전 목록 형식도 읽는다.
- 로컬 인사말의 유무와 별개로 가져오기 성공 여부를 검사한다. 실패하면 다음 방 입장 또는 앱 복귀 때 재시도한다.
- 서버 조회와 병합 저장을 모두 완료했을 때 성공을 확정한다. 빈 서버 기록도 성공으로 기록하고, 로컬 전용 ChatService는 서버 가져오기를 완료한 것으로 표시하지 않는다.
- 재실행 후에도 완료된 가져오기를 반복하지 않는다. 서버 기록 내부에 동일한 문구가 여러 번 있어도 보존한다.
- 전체 집합으로 같은 문구를 제거하던 방식 대신 과거 기록 끝과 로컬 기록 시작의 연속된 겹침만 처리한다. 현재 ChatLine 계약에는 메시지 ID가 없어, 경계에서 우연히 동일한 작성자/문장이 나온 경우를 완전히 구분할 수는 없다. 향후 서버 메시지 ID를 주고받으면 이 부분을 더 정확하게 처리할 수 있다.
- 서버의 기존 최근 30개 조회 범위는 유지하며, 서버 전체 대화 페이지네이션을 추가한 작업은 아니다.

## 검증

- 전체 Flutter 테스트 613개 통과, 조건부 3개 건너뜀. 정적 분석 이상 없음.
- 최종 병합 완료 상태 재확인 후 신규 복구 테스트 11개 재통과.
- 구조 손상 시 백업 선택, 주문 덮어쓰기 차단, 보류 후 동일 저장소 재시도, 두 사본 격리 보존, 앱 복구 안내의 두 선택 동작, 첫 오프라인 방문 후 다음 입장의 서버 조회, 저장 실패 시 재시도, 반복 메시지 보존, 캐시 읽기 횟수, 큰 JSON/null 문서 호환을 검증했다.
- 최종 iPad Pro 12.9 시뮬레이터 빌드·실행·화면 확인 완료.
- 유선 iPad (78)에 `lib/main.dart` 릴리스 업데이트 설치·실행 완료. native-assets 개발 팀 서명 확인. 기존 저장 파일 19개가 업데이트 전후 바이트 동일했다. 손상 시나리오는 임시 파일/테스트 저장소에서 검증했으며 실제 사용자 데이터를 손상시키거나 초기화하지 않았다.
